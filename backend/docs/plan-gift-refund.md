# 套餐赠送与退款记账

## 范围

本文说明站内 CNY 订单的金额规范化、套餐赠送余额的记账，以及管理员退款审批的记账。它不涉及 LLM 网关的扣费协议；支付宝原路退款见 `internal/biz/self_refund.go`。

## 订单金额

- 创建余额订单和套餐订单时，使用 `decimal` 将 CNY 金额乘以 100、四舍五入为整数分，再除以 100 存入 `site_orders.amount`。
- 小于半分且规范化后为 0 的金额会被拒绝。
- 支付下单、支付回调校验、`MarkOrderPaid` 入账和后续可退款上限使用同一个整数分结果。
- `MarkOrderPaid` 也会规范化历史 pending 订单并回写金额，因此例如 `1.00499999` 只会支付、入账和退款 `1.00`，不会按 100 分支付却按原始小数入账。

全流程不使用 `float` 计算订单金额。

## 赠送余额账

套餐 `initial_balance` 不再写普通 `topup`，而是写 `balance_txes.kind = gift`。每条赠送或冲销流水都通过 `related_user_plan_id` 关联产生赠送的用户套餐：

- 正数 `gift`：套餐生效时发放的赠送；
- 负数 `gift`：套餐退款获批时注销的剩余赠送。

计费仍扣统一的 `users.balance`。退款审批持有用户行锁，并按不可变余额流水重放赠送余额：

1. 正数 `gift` 建立赠送批次；
2. 消费、转出等负数流水按“赠送优先、先进先出”消耗赠送批次；现金退款流水只撤回实付，不消耗赠送；
3. 负数 `gift` 只冲销其关联套餐的批次；
4. 最终冲销额不会超过用户当前可用余额。

这样不需要修改网关扣费热路径，仍可审计并重算每个套餐的剩余赠送。

`gift` 与现金 `topup` 分开，因此邀请活动的 `any_topup` / `min_topup` 统计不会把套餐赠送当作实付充值。

## 套餐退款审批

`ApproveRefund` 对套餐订单在同一事务中：

1. 锁定 pending 退款和对应订单；
2. 取消 `user_plan`；
3. 锁定用户并冲销该套餐的剩余赠送；
4. 批准退款，并按订单实付金额计算部分或全额退款状态。

赠送金额不进入可退款金额。

`CancelOrder`、`MarkOrderPaid`、`ApproveRefund` 和 `RejectRefund` 均采用行锁及带原状态条件的更新，避免事务外读取 pending 后覆盖并发写入的终态。

## 已消费的赠送

用户可以在无理由退款期内先用完赠送余额，再申请退还全部实付金额。退款只注销尚未消费的赠送，已消费的部分不从实付退款中扣减。
